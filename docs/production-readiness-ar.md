# بوابة الإطلاق الإنتاجي

> تحديث الاستضافة: اختير Vercel؛ اتبع `docs/vercel-deployment-ar.md` بدل خطوات Docker أدناه. أضيف تخزين S3 وفحص خارجي إلزامي قبل الحفظ، وحد دخول مشترك عبر PostgreSQL. الأمثلة التالية لـDocker بديل فقط وليست إعداد Vercel. التهيئة الأولية أصبحت بأمر مستقل `python -m scripts.initialize_production` بعد تطبيق migration 0001 و0002، لا عند بدء التطبيق.

## الحالة الفعلية

هذه التغييرات تقوي النشر لكنها **ليست شهادة جاهزية إنتاجية أو مالية**. لا تدخل بيانات حقيقية قبل إكمال قائمة القبول أدناه. الاختبارات المحلية: 27 ناجحة على SQLite وPython 3.11. لم يتوفر Docker أو خادم PostgreSQL في بيئة التنفيذ المحلية؛ أضيف مسار CI لتطبيق مخطط PostgreSQL وفحص بدء الإنتاج على Python 3.12، ولم نتحقق من نتيجته بعد.

## الحمايات المنفذة

- رفض SQLite والأسرار الافتراضية والكوكيز غير الآمنة في وضع الإنتاج.
- عدم إنشاء الجداول تلقائيًا في الإنتاج؛ التحقق من وجود جميع الجداول. هذا ليس بديلًا عن إدارة إصدارات المخطط ومراجعة قيوده.
- اشتراط كلمة مرور أولية لا تقل عن 16 حرفًا عند إنشاء المدير فقط. يمكن حذفها من إعداد النشر بعد نجاح الإنشاء؛ أبقِ البريد الأولي ثابتًا لتجنب إنشاء مدير جديد.
- حماية عمليات تعديل API من CSRF بترويسة `X-Sawa-Request: 1` ومطابقة Origin إن وُجد. لا تفعّل CORS عامًا. عملاء API غير المتصفح يجب أن يرسلوا الترويسة أيضًا.
- إخفاء Swagger وOpenAPI في الإنتاج، وإضافة ترويسات أمان ومنع تخزين استجابات API مؤقتًا.
- nginx ينهي TLS ويحد محاولات الدخول لكل عنوان IP؛ التطبيق وقاعدة البيانات بلا منافذ منشورة في ملف الإنتاج.
- منع الموظفين المقيدين من رفع/قراءة مستندات بلا نطاق نشاط.
- رفع المستندات في الإنتاج يتطلب S3 وماسح HTTPS خاص؛ رفض الملف أو تعطل الفحص يمنع التخزين. لم تختبر الخدمات الخارجية فعليًا بعد.
- فصل الأسرار والبيانات وشهادات TLS عن Git وسياق بناء Docker.
- ملف اعتماديات مثبت `requirements.lock` مستخدم في Docker وCI؛ يلزم تحديث أمني دوري وفحص الثغرات، وليس التثبيت وحده ضمانًا للأمان.

## تحضير النشر (خادم Linux مع Docker Compose)

1. انسخ `.env.example` إلى `.env`، وقيّد صلاحياته `chmod 600 .env`.
2. أنشئ سرًا مختلفًا لكل من SECRET_KEY وكلمة مرور المدير وكلمة مرور PostgreSQL. استخدم قيمًا عشوائية URL-safe لكلمة مرور قاعدة البيانات لأنها مضمنة في URL. لا تستخدم قيم المثال.
3. ضع `APP_ENV=production` و`COOKIE_SECURE=true` و`PUBLIC_ORIGIN=https://your-real-domain` دون شرطة أخيرة. اضبط البريد الحقيقي للمدير.
4. وفر شهادة موثوقة ومفتاحها في `deploy/tls/fullchain.pem` و`deploy/tls/privkey.pem` مع صلاحيات مقيدة وخطة تجديد مراقبة. لا تضفها إلى Git.
5. راجع ملف SQL مع مسؤول PostgreSQL قبل أول إنشاء. يطبق Compose المخطط فقط عند تهيئة volume فارغ؛ لن يرقّي قاعدة بيانات موجودة. **لا تحذف volume لإجبار التهيئة.**
6. شغّل:

```bash
docker compose --env-file .env -f compose.production.yml up -d --build
docker compose --env-file .env -f compose.production.yml ps
```

7. افحص `/health` و`/ready` عبر النطاق وشهادة TLS، ثم تسجيل الدخول والخروج وصلاحيات كل دور. `/health` لنبض الخدمة، و`/ready` يختبر اتصال قاعدة البيانات.
8. امنع أي كشف مباشر للمنفذ 8000 أو 5432. أبق nginx نقطة الدخول الوحيدة كي لا يمكن تجاوز محدد الدخول. إذا أضفت CDN أو وكيلاً آخر فاضبط trusted real IP بدقة؛ لا تثق بترويسات العميل عشوائيًا.

## النسخ الاحتياطي والاستعادة — يجب تجربة الاستعادة قبل الإطلاق

نفذ في جلسة shell مقيدة، ثم انقل النسخ مشفرة إلى موقع خارجي مع احتفاظ ومراقبة حسب سياسة المؤسسة:

```bash
mkdir -p backups
chmod 700 backups
umask 077
docker compose --env-file .env -f compose.production.yml exec -T db pg_dump -U sawa_app -d sawa_united -Fc > backups/sawa.dump
# افحص بنية النسخة؛ هذا لا يغني عن الاستعادة التجريبية.
docker compose --env-file .env -f compose.production.yml exec -T db pg_restore --list < backups/sawa.dump
```

للتجربة أنشئ **قاعدة منفصلة فارغة** واستعد فيها، ولا تستعد فوق بيانات الإنتاج:

```bash
docker compose --env-file .env -f compose.production.yml exec -T db createdb -U sawa_app sawa_restore_check
docker compose --env-file .env -f compose.production.yml exec -T db pg_restore -U sawa_app -d sawa_restore_check --exit-on-error --single-transaction < backups/sawa.dump
```

تحقق من الأعداد والعلاقات ومبالغ عينة مالية وتسجيل الدخول على بيئة معزولة. النسخة تحتوي بيانات حساسة وبصمات اعتماد: لا ترفعها إلى Git ولا ترسلها في المحادثة. إذا وجدت مستندات سابقة فانسخ volume الملفات أيضًا مع لقطة متسقة. حدد RPO/RTO وجدولة النسخ ومراقبة فشله مع مسؤول التشغيل.

## شروط ما زالت تمنع اعتماد البيانات الحقيقية

- نجاح CI وفحص PostgreSQL الفعلي، واختبارات تزامن المخزون والحجوزات والتحصيل تحت حمل واقعي.
- مراجعة شاملة للصلاحيات وربط السجلات العابرة للأنشطة واختبارات اختراق مستقلة؛ الإصلاح الخاص بالمستندات لا يمثل مراجعة لكل المسارات.
- مراجعة واعتماد المحاسب للقيم والكسور والعملات والتسويات والرديات، والمستشار القانوني للعقود. وحدات مالية متقدمة لم تنفذ بعد كما يوضح README.
- MFA للحسابات الإدارية، وإدارة دورة حياة الحسابات واستعادة كلمات المرور بأمان.
- migrations مُدارة ومُرقمة مع خطة ترقية وتراجع مجربة؛ المخطط الأولي ليس نظام ترحيلات كاملًا.
- فحص برمجيات خبيثة وتخزين مشفر مع سياسة احتفاظ قبل تمكين رفع المستندات.
- تجربة استعادة ناجحة خارج الخادم، مراقبة وتنبيهات، تحديثات أمنية وفحص اعتماديات وصور الحاويات.
- اختبار قبول المستخدمين واعتماد مسؤول المشروع وتحديد نطاق الإطلاق.

## معلومات مطلوبة لاستكمال الإطلاق

النطاق ومزود الاستضافة، الدول والمتطلبات التنظيمية، عدد المستخدمين والحمل المتوقع، هل الرفع مطلوب يوم الإطلاق، أهداف الاستعادة وفقد البيانات المقبول، ومزود MFA والتخزين. لا ترسل كلمات المرور أو مفاتيح الإنتاج في المحادثة.
